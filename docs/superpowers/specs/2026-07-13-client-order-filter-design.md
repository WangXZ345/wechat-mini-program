# 客户端“我的订单”组合筛选设计

日期：2026-07-13

## 1. 目标

在现有微信小程序客户端“我的订单”页面增加组合筛选能力，同时保留当前订单处理阶段标签和订单详情流程。

用户可以：

- 按订单号或商品名称搜索；
- 按全部、今天、近 7 天、近 30 天或自定义起止日期筛选；
- 同时选择多个付款状态；
- 同时选择多个配送状态；
- 将上述条件与现有订单处理阶段组合使用；
- 查看准确覆盖历史订单的分页结果，而不是只过滤当前已加载的一页。

本次不新增数据库集合、订单字段或搜索索引，不修改下单、库存、付款、账款、后台订单、权限或导出流程。

## 2. 已确认的产品决策

- 目标入口是客户端 `miniprogram/pages/order/list`，不是后台订单管理页。
- 页面采用“常驻搜索栏 + 筛选按钮/抽屉 + 已应用条件标签”的布局。
- 付款状态和配送状态在各自维度内均允许多选。
- 时间筛选包含自定义起止日期。
- 每次重新进入“我的订单”都恢复默认条件，不在本地持久化筛选状态。从订单详情返回订单页也视为重新进入，恢复默认条件。
- 点击“清除”会清空关键词、时间、付款状态和配送状态，并将处理阶段恢复为“全部”。
- 查询由现有 `getOrders` 云函数完成，不能只在前端过滤已加载订单。

## 3. 用户界面

页面顶部从上到下排列：

1. 订单号/商品名称搜索栏；
2. “筛选”按钮及当前已应用的详细条件数量；
3. 已应用条件标签和“清除”入口；
4. 现有处理阶段横向标签；
5. 订单列表。

搜索框使用“搜索订单号 / 商品名称”作为占位文案。输入过程不调用云函数；用户点击键盘“搜索”后才应用关键词并重新加载第一页。

点击“筛选”打开底部抽屉。抽屉内使用 `draftFilters`，包含：

- 时间：全部、今天、近 7 天、近 30 天、自定义；
- 自定义开始日期和结束日期；
- 付款状态多选项；
- 配送状态多选项；
- “重置”和“应用筛选”按钮。

“应用筛选”校验通过后，将 `draftFilters` 复制为 `appliedFilters`，关闭抽屉并重新加载第一页。“重置”只重置抽屉草稿；“清除”重置页面全部已应用条件。

已应用条件以紧凑标签展示。单项状态显示对应名称，多项状态显示“付款 N 项”或“配送 N 项”。处理阶段由原有横向标签明确展示，不重复生成条件标签。

自定义日期按本地自然日计算，开始时间为所选日期 00:00:00.000，结束时间为所选日期 23:59:59.999。开始日期晚于结束日期时阻止提交，并显示“开始日期不能晚于结束日期”。

## 4. 前端状态与请求

订单页维护以下新增状态：

- `searchKeyword`：搜索框当前文本；
- `draftFilters`：抽屉内尚未应用的时间和状态选择；
- `appliedFilters`：当前生效的筛选条件；
- `filterDrawerVisible`：抽屉显示状态；
- `activeFilterCount`：已应用详细条件数量；
- `nextCursor`：筛选分页游标。

原有 `activeOrderFilter` 继续表示处理阶段，但不再只对当前 `orders` 数组进行最终筛选。加载订单时将其作为 `orderStage` 发送给云函数，确保处理阶段与其他条件覆盖完整历史订单。

新的客户端筛选请求结构为：

```js
{
  summaryOnly: true,
  pageSize: 10,
  cursor: nextCursor || "",
  filters: {
    orderStage: "all",
    startDate: "",
    endDate: "",
    paymentStatuses: [],
    deliveryStatuses: [],
    keyword: ""
  }
}
```

`cursor` 对客户端是不透明字符串。首次查询或筛选条件变化时传空字符串；加载更多时使用上次响应的 `nextCursor`。未使用新筛选参数的旧调用继续使用现有 `page`/`pageSize` 行为。

返回结构在现有字段基础上增加 `nextCursor`：

```js
{
  orders: [],
  page: 1,
  pageSize: 10,
  hasMore: false,
  nextCursor: ""
}
```

前端必须以订单 `_id` 去重，避免筛选期间新增订单或游标边界变化导致重复卡片。

## 5. `getOrders` 筛选流程

### 5.1 用户隔离和参数标准化

客户查询始终先设置 `where.userOpenid = cloud.getWXContext().OPENID`。客户端传入的 `userOpenid`、`admin` 或其他越权字段不得改变客户查询范围。

筛选参数只接受白名单字段，并执行以下限制：

- 关键词去除首尾空白并限制为最多 64 个字符；
- 每个状态数组去重并限制为最多 10 项；
- 忽略不在白名单中的状态值；
- 无效日期返回明确、安全的参数错误；
- 开始日期晚于结束日期返回参数错误。

### 5.2 结构化条件

日期条件优先加入数据库 `where.createdAt`，缩小候选范围。

付款状态使用面向用户的规范组，兼容历史别名：

- 未付款：`none`、`unpaid`；
- 待确认：`pending_confirm`；
- 部分付款：`partial`、`partial_paid`；
- 已付款：`paid`；
- 付款异常：`abnormal`；
- 已退款：`refunded`。

配送状态按现有 `shippingStatus`、`deliveryStatus` 和 `shipmentDisplay.shippingStatus` 统一标准化。面向用户的选项包括待处理、待自提、已自提、待发货、已发货、已完成和售后中；历史值 `created`、`pending_shipment`、`waiting_shipping` 归入待发货。

由于旧订单可能把配送状态写在不同字段，配送多选和处理阶段匹配在订单摘要整形后执行，不能仅依赖单一数据库字段。

### 5.3 关键词和处理阶段

关键词统一转为小写、压缩空白并移除常见标点，匹配：

- `orderNo`；
- 当前订单所有商品项的 `productName`。

关键词不得匹配或返回手机号、地址、`openid`、管理员备注、风险字段、付款截图或交易号。

现有处理阶段语义保持不变：全部、审核中、待付款、待确认、待发货、已完成。阶段判断复用当前页面的状态组合语义，并迁移为可测试的共享纯函数或在前后端分别使用同一份明确映射，避免页面显示与云函数筛选不一致。

### 5.4 批量扫描和游标

数据库先按当前用户和日期倒序读取候选订单。云函数每批读取 50 条候选，单次调用最多扫描 500 条。每批加载订单商品摘要和配送摘要，执行管理员字段剥离、地址脱敏、状态标准化、关键词匹配和处理阶段匹配，直到：

- 收集到 `pageSize` 条匹配订单；或
- 候选订单已经耗尽；或
- 达到单次调用的安全扫描上限。

达到 500 条扫描上限但仍有候选订单时，返回非空 `nextCursor` 和 `hasMore: true`。如果本次没有匹配项，前端自动连续请求最多 2 个后续游标；仍无结果但 `hasMore: true` 时显示“继续查找更早订单”，由用户继续触发。前端不得把这种状态显示为最终空结果。这样既覆盖较早历史订单，也避免单次云函数调用或一次页面操作无限扫描。

旧的无筛选分页路径保持原样，订单详情 `orderId` 查询和后台 `admin: true` 查询不改为新游标路径。

## 6. 安全和兼容

- 客户订单仍在返回前执行 `stripAdminFields` 和现有地址脱敏。
- 不向普通用户新增库存、成本、管理员备注、标签、风险、付款截图地址、交易号、完整手机号或完整地址。
- 不更改 `getOrders` 的管理员权限判断和后台筛选语义。
- 不修改 `createOrder`、`submitCartOrder` 或历史订单数据。
- 不要求数据迁移或建立新的搜索索引。
- 原有订单详情、下拉刷新、加载更多和自定义 tabBar 行为保持兼容。

## 7. 加载、空状态和错误处理

- 首次进入且没有缓存列表时显示现有骨架屏。
- 已有订单时应用筛选采用静默刷新并锁定重复提交，查询失败时保留旧列表。
- 参数错误显示对应用户文案，不展示堆栈、数据库条件或内部字段。
- 只有 `hasMore: false` 且没有匹配订单时才显示“没有符合条件的订单”。
- 没有匹配项但 `hasMore: true` 时显示查找中状态；自动续查达到 2 次后显示“继续查找更早订单”。
- 空结果提供“清除筛选”入口。
- 加载更多失败时保留已加载订单，并允许用户重试。
- 页面重新进入时清空所有筛选状态并从默认条件加载。

## 8. 修改范围

计划修改：

- `miniprogram/pages/order/list.js`
- `miniprogram/pages/order/list.wxml`
- `miniprogram/pages/order/list.wxss`

仅在确有必要时调整 `miniprogram/pages/order/list.json`，例如声明已存在项目体系中的弹层组件；优先使用原生页面结构，不新增运行时依赖。

明确不修改：

- `miniprogram/pages/admin/orders.*`
- `miniprogram/app.json`
- `createOrder`、`submitCartOrder` 等写入云函数
- 数据库集合、索引和订单字段
- 付款、账款、库存、审核、发货、售后、退款和导出业务逻辑

## 9. 测试与验收

### 9.1 云函数自动化测试

扩展 `cloudfunctions/getOrders/index.test.js`，覆盖：

- 客户查询始终限制为当前 `openid`；
- 日期起止边界和无效日期；
- 付款状态多选及历史别名；
- 配送状态多选及旧字段兼容；
- 订单号关键词；
- 任意商品名称关键词，而不只匹配第一件商品；
- 处理阶段与其他条件组合；
- 跨候选批次找到匹配订单；
- `nextCursor`、`hasMore`、去重和最终耗尽；
- 非法状态、超长关键词和越权参数；
- 返回结果继续剥离管理员和敏感字段；
- 旧的客户分页、订单详情和后台查询保持兼容。

### 9.2 静态检查

- 对修改的 JS 文件运行 Node 语法检查；
- 解析相关 JSON 文件；
- 检查 WXML 事件名、`data-*` 参数和 JS 方法一致；
- 检查移动端窄屏下搜索栏、筛选按钮、条件标签和抽屉不溢出。

- 关键词按订单号和非首件商品名称均能命中；
- 快捷时间和自定义时间边界正确；
- 付款和配送状态可多选并可组合；
- 处理阶段与详细条件共同生效；
- 条件标签、数量、重置和清除行为正确；
- 筛选结果加载更多无重复、遗漏或不匹配订单；
- 无结果、网络失败和重试反馈正确；
- 从订单详情返回后恢复默认筛选；
- 原有订单详情、下拉刷新和 tabBar 行为正常。

## 10. 部署边界

本次实现完成后默认只保留本地修改：

- 需要上传的云函数：`getOrders`；
- 只需重新编译或预览的小程序文件：`miniprogram/pages/order/list.*`；
- 未改动并保持兼容：订单写入、后台订单、付款、库存、账款、审核、发货、售后、退款和导出入口。

未经用户再次明确确认，不上传云函数、不发布小程序、不连接生产环境执行写操作。
