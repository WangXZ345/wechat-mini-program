# 首页商品首次打开提速设计

## 1. 背景与目标

用户从首页首次点击任意商品时，页面路由已经开始切换，但首页画面仍会停留一段时间，之后详情页才出现。当前代码已经实现公开商品快照先显，且 `getProducts` 已按 `productId` 精确读取，因此本轮不再扩大到商品查询云函数或商品数据结构改造。

本轮目标是缩短“点击首页商品”到“商品详情第一帧可见”的等待时间，同时保持商品、价格、收藏、配送、地址、加购和预下单的现有业务语义。

完成条件：

- 首页点击链路不再在 `wx.navigateTo` 前执行同步持久化写入。
- 详情页能够从短生命周期内存快照立即恢复公开商品信息。
- 商品精确查询和配送相关查询仍会执行，但不得阻塞快照首帧。
- 快照不得包含真实库存、成本、供应商、内部标签、管理员备注等敏感字段。
- 快照缺失、过期、商品不匹配或网络失败时，页面保持现有安全回退和错误提示。

## 2. 已确认根因与边界

首页当前在 `wx.navigateTo` 前调用 `writeProductPreview(product)`。该调用最终执行 `wx.setStorageSync`，首次本地存储初始化或设备存储较慢时会直接推迟导航；写入失败又是 best-effort，详情页可能无法命中预览。

详情页在鉴权和云函数调用前已经尝试读取商品预览。预览命中时理论上可以立即渲染，因此本轮优先修复预览传递方式和首帧调度，不重新设计详情页 UI。

以下内容不在本轮范围内：

- 不修改 `getProducts`、`searchProducts` 或其他云函数。
- 不调整商品、库存、订单、付款、账款、地址或权限业务规则。
- 不迁移商品详情路由到分包。
- 不新增外部依赖、图片服务或远程素材。
- 不上传云函数、不发布小程序、不连接生产环境执行写操作。

## 3. 方案选择

### 3.1 采用方案：内存快照 + 立即导航 + 首帧后校准

点击商品时，使用现有公开字段白名单生成轻量商品快照，写入进程内短生命周期缓存，然后立即调用 `wx.navigateTo`。详情页优先消费内存快照，未命中时再读取现有持久缓存。详情首帧提交后，才启动商品精确校准以及配送、地址相关请求。

持久商品预览继续作为二级兜底，但首页点击链路不再写持久缓存。详情页从服务端取得精确商品结果后，才使用现有同步接口刷新持久预览；因此点击路径没有存储等待，也不存在旧异步写覆盖精确结果或恢复已清除商品的竞态。

### 3.2 未采用方案

- 仅把持久缓存改为异步写入：详情页可能早于写入完成，仍会偶发预览未命中。
- 首页导航成功后异步持久化公开预览：最终审查证明它需要处理旧异步写、精确写、清除、过期和并发写的复杂顺序；该复杂度对首帧没有必要，因此在 2026-07-16 的架构复核中明确废止。
- 商品详情迁入预加载分包：可能改善代码冷加载，但涉及路由打包和更大的兼容验证，本轮收益证据不足。
- 首页预取多个商品完整详情：会放大云函数调用量，且可能加载用户根本不会打开的商品，不符合兼容和容量约束。

## 4. 架构与组件职责

### 4.1 `miniprogram/utils/performanceCache.js`

在现有商品预览白名单基础上增加进程内预览通道，职责为：

- 复用 `publicProductPreview` 生成脱敏公开快照。
- 按 `productId` 保存，避免不同商品之间串用。
- 使用短 TTL，并在成功读取后消费或主动清理。
- 支持读取时校验 `productId`、数据结构和过期时间。
- 保留现有持久缓存 API 作为二级兜底。

内存快照只存在于当前小程序进程，不跨登录、不跨重启，不作为业务事实来源。

### 4.2 `miniprogram/pages/index/index.js`

`goDetail` 调整为：

1. 从首页商品或当前可见推荐商品中找到目标商品。
2. 生成并写入内存公开快照。
3. 立即执行 `wx.navigateTo`。
4. 不在首页点击或导航回调中写持久商品预览。

导航只依赖进程内公开快照。持久预览由详情页精确商品结果刷新，持久缓存错误不得阻止商品展示，也不显示业务错误提示。

### 4.3 `miniprogram/pages/product/detail.js`

详情页加载顺序调整为：

1. 解析并保存 `productId`。
2. 优先消费进程内快照；未命中时读取持久商品预览。
3. 命中任一快照后立即设置 `product`、`loading: false`、`initialized: true` 并计算金额。
4. 使用 `wx.nextTick` 或等价的首帧后调度启动后台校准。
5. 调用 `getProducts({ onlyActive: true, productId })` 获取服务端最新公开商品信息。
6. 商品校准完成后保持现有收藏状态加载逻辑。
7. 配送偏好、设置和默认地址在首帧后异步加载，保持当前默认值和错误处理。

无快照时继续显示现有 skeleton，并通过精确商品查询完成初始化。商品不存在或已下架时，必须清除对应快照并显示现有不可用状态。

## 5. 数据流

正常命中路径：

`首页公开商品 -> 生成脱敏内存快照 -> navigateTo -> 详情页消费快照 -> 第一帧 -> 精确商品校准 + 配送数据加载 -> 更新最新展示并持久化精确公开预览`

回退路径：

`内存快照未命中 -> 持久预览缓存 -> 仍未命中则 skeleton -> getProducts(productId) -> 正常详情或不可用状态`

服务端精确商品结果始终拥有最终展示优先级；任何快照都不能绕过上下架、删除状态、下单、加购、地址归属或库存的服务端校验。

## 6. 错误处理与安全

- 内存快照暂存失败：继续导航，详情页走持久预览或 skeleton 回退。
- 精确结果持久预览写入失败：保持当前精确商品展示，不影响收藏、配送、加购或预下单。
- 快照过期、格式异常或 `productId` 不一致：忽略并清理，不展示错误商品。
- 精确商品查询失败：保留已经显示的公开快照，沿用现有错误提示，不伪造请求成功。
- 商品不存在或已下架：清除快照，显示现有“商品不可用”状态。
- 配送相关请求失败：沿用当前提示和默认状态，不影响公开商品首帧。
- 内存和持久快照仅允许公开白名单字段；不得加入库存、成本、供应商、后台备注、内部标签或客户信息。

## 7. 测试与验证

实施采用 TDD，先增加失败测试再修改实现。至少覆盖：

- 首页点击商品时，导航启动不依赖同步 `wx.setStorageSync`。
- 首页列表商品和推荐商品都能生成正确的公开快照。
- 详情页优先读取内存快照，并在首轮网络请求完成前结束 skeleton。
- 内存快照过期、商品 ID 不匹配或格式异常时不会被使用。
- 公开快照不包含敏感字段。
- 无快照时仍按原流程调用 `getProducts({ productId })`。
- 精确结果返回后会替换快照展示；下架或不存在时清除快照。
- 配送和地址请求在首帧调度后启动，但参数、返回处理和业务默认值不变。

静态验证：

- 修改的 JS 使用 bundled Node 执行 `--check`。
- 相关测试全部通过。
- 扫描商品预览白名单和详情 WXML，确认没有敏感字段新增。
- 对修改文档和代码做 UTF-8 替换字符检查。

微信开发者工具验收：

1. 重新编译后首次从首页点击任意商品，观察是否立即开始详情转场。
2. 对比首次打开、返回后打开另一个商品、再次打开同一商品三组场景。
3. 确认详情标题、价格和缩略图先显，随后服务端最新字段正常校准。
4. 确认收藏、配送、地址、加购和立即预下单仍可用。
5. 检查 Console、Network 和页面路径，确认没有新增错误或重复导航。

- `miniprogram/utils/performanceCache.js`
- `miniprogram/pages/index/index.js`
- `miniprogram/pages/product/detail.js`
- 对应新增或调整的前端测试文件

不修改云函数、集合、字段、权限和导出逻辑。实施完成后只需要在微信开发者工具中重新编译、预览和真机验收；没有需要上传的云函数。
