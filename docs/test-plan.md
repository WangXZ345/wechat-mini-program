# 测试流程

## 1. 管理员初始化

1. 导入项目并开通云开发。
2. 部署所有云函数。
3. 运行小程序登录一次，确认 `users` 集合出现当前 openid。
4. 把该 openid 添加到 `admin_users`，并设置 `isActive: true`。
5. 重新进入后台首页，确认可以访问。

## 2. 商品和库存

1. 后台进入“商品管理”。
2. 新增商品，价格填写整数分，例如 `19900`。
3. 库存填写 `10`，设置上架。
4. 用户端首页应能看到商品，但不能看到库存数量。
5. 后台“库存管理”应能看到库存和管理员调整日志。

## 3. 库存充足自动审核

1. 用户端进入商品详情，下单数量填写 `2`。
2. 提交后订单进入自动审核中。
3. 等待约 10 秒，或在订单详情点击刷新审核结果。
4. 订单应变为“已通过待支付”。
5. 后台库存应减少 2，并生成库存日志。
6. 客户账款应增加对应订单金额。

## 4. 库存不足人工审核

1. 用户端下单数量填写大于当前库存。
2. 订单应进入“待管理员审核”，用户端不显示具体库存原因。
3. 后台订单管理中可以看到该订单。
4. 管理员批准时会再次检查库存；库存不足时不能批准。
5. 管理员拒绝后，用户端订单显示未通过。

## 5. 付款截图

1. 对已通过订单进入支付页。
2. 选择支付方式并上传付款截图。
3. 订单状态变为“待确认付款”。
4. 后台订单管理查看截图，并标记已付款、部分付款或付款异常。
5. 标记已付款后，客户账款未付金额应减少。

## 6. 权限校验

1. 移除当前 openid 的管理员权限。
2. 尝试访问后台页面或调用后台云函数。
3. 应提示无管理员权限。
4. 普通用户不能通过 `getProducts` 获取库存字段。
# 管理员备注 / 客户备注测试流程

1. 使用 `admin_users` 中的管理员账号进入后台订单管理。
2. 在订单卡片打开“管理员备注”，输入 500 字以内内容并保存，应提示“备注已保存”。
3. 刷新订单列表，订单应显示“有备注”标签和 20 字以内备注摘要。
4. 再次打开同一订单备注，不修改直接保存，应提示“备注未修改”，不应新增无效日志。
5. 点击“修改记录”，应看到本次修改的修改前/修改后备注、操作人和时间。
6. 点击“清空备注”，确认后二次保存，应清空备注且新增一条日志。
7. 使用普通用户进入订单详情，确认页面不展示 `adminNote`、`adminTags`、`riskLevel`、`riskLevelSnapshot`。
8. 后台进入“客户管理”，打开客户详情，添加客户备注、标签，设置 `important` 后保存。
9. 返回客户列表，应显示“重要客户”标识、标签和“有客户备注”摘要。
10. 将客户风险等级改为 `slow_pay`，创建订单后后台订单列表应显示“付款慢”提醒。
11. 将客户风险等级改为 `risk`，创建商品订单和购物车订单，订单状态应为 `pending_admin`，前台只看到“订单已提交，请等待商家确认”。
12. 对 `risk` 客户订单手动调用自动审核刷新，订单仍应保持待管理员审核，不能自动通过。
13. 将客户风险等级改为 `blocked`，创建商品订单和购物车订单都应失败，前台提示“当前账号暂无法下单，请联系商家。”。
14. 使用非管理员账号调用 `updateOrderAdminNote`、`updateCustomerAdminNote`、`getNoteLogs`、`getAdminCustomerDetail`，都应返回无管理员权限。
15. 输入超过 500 字订单备注、超过 1000 字客户备注、超过 20 个标签或超过 10 字单个标签，应保存失败并提示。

## 7. 付款状态自动汇总 / 客户账款中心

1. 创建一笔库存充足订单并完成自动审核，订单应为 `approved_pending_payment`，`paymentStatus` 为 `unpaid`，`paidAmount` 为 0，`unpaidAmount` 等于 `totalAmount`。
2. 检查 `customer_accounts`：`totalOrderAmount`、`totalUnpaidAmount`、`todayOrderAmount` 增加，`account_logs` 写入 `order_approved`。
3. 重复触发同一订单的账款计入逻辑，`orders.accountIncluded` 应阻止重复增加账款。
4. 用户在付款页应看到今日订单金额、历史未付金额、待确认付款金额和本次应付总额。
5. 用户上传付款截图后，订单应变为 `pending_payment_confirm`，`paymentStatus` 为 `pending_confirm`，并写入一条 `payment_records.confirmStatus = pending`。
6. 待确认付款金额应汇总到 `customer_accounts.pendingConfirmAmount`。
7. 后台订单管理点击“确认已付款”，订单应变为 `paid`，`paidAmount` 等于订单金额，`unpaidAmount` 为 0。
8. 全额确认后，`payment_records` 写入 `confirmed`，`account_logs` 写入 `payment_confirmed`，客户累计已付增加、当前未付减少。
9. 重新创建订单并提交截图，后台点击“部分付款”，输入小于未付金额的实收金额，订单应变为 `partial_paid`，剩余金额继续计入未付。
10. 部分付款后再次提交截图并确认剩余金额，订单应变为 `paid`，且不会重复累计前一次实收金额。
11. 标记付款异常后，订单 `paymentStatus` 为 `abnormal`，客户 `abnormalCount` 和 `abnormalAmount` 应更新。
12. 驳回付款截图后，订单回到 `approved_pending_payment`，`paymentStatus` 为 `unpaid`，不增加已付金额。
13. 同一客户一天内多个已批准订单，`todayOrderAmount` 应等于当天批准订单金额合计。
14. 非当天已批准但未付订单，应计入 `historyUnpaidAmount`，付款页本次应付总额等于今日新增加历史未付。
15. 后台客户账款中心可以按未付款、今日有下单、待确认付款、付款异常、风险客户、已结清筛选。
16. 后台客户账款详情应展示客户基础信息、汇总金额、订单明细、付款记录和账款流水。
17. 管理员设置 `riskLevel = risky` 后，商品订单和购物车订单应进入 `pending_admin`。
18. 管理员设置 `riskLevel = blocked` 后，商品订单和购物车订单应创建失败，并提示当前账户暂不可下单。
19. 管理员标记已结清时必须填写备注，完成后客户当前未付为 0，订单写入 `settlementStatus = manual_settled`，流水写入 `manual_settled`。
20. 管理员点击重算账款后，`customer_accounts` 汇总金额应与该客户订单明细一致。
21. 管理员导出客户对账单后，应生成 Excel，包含客户汇总、订单明细、付款明细，并写入 `export_records`。
22. 普通用户调用后台账款接口、风险接口、结清接口、导出接口时，应返回无管理员权限。

## 8. 配送方式和发货管理

1. 管理员进入后台“业务配置”，填写自提地址、自提时间、联系人、联系电话和备注并保存。
2. 新用户进入商品详情页，配送方式默认显示后台默认值；当前实现默认 `shipping`。
3. 用户选择自提并提交商品订单，`orders.deliveryType` 应为 `self_pickup`，`pickupInfo` 应保存自提配置快照，`deliveryStatus` 初始为 `pending`。
4. 用户选择发货并填写收货人、手机号、地址后提交商品订单，`orders.deliveryType` 应为 `shipping`，`shippingAddress` 应保存本次地址快照。
5. 用户下次进入商品详情页或购物车页，应自动选中上次配送方式。
6. 用户上次选择发货时，下次应自动带出 `users.lastShippingAddress`。
7. 用户上次选择自提时，下次应默认选中自提，并展示最新后台自提配置。
8. 购物车勾选多个商品提交时，整个订单只保存一个 `deliveryType`。
9. 选择发货但不填收货人、手机号或详细地址时，云函数应拒绝提交。
10. 手机号格式错误时，云函数应拒绝提交。
11. 自提配置缺失时，选择自提提交订单应失败并提示联系商家。
12. 订单通过审核后仍应停留在待付款流程，`deliveryStatus` 不应直接变为待发货或待自提。
13. 后台确认付款为已付款后，自提订单 `deliveryStatus` 应变为 `waiting_pickup`，发货订单应变为 `waiting_shipping`，并写入 `delivery_logs`。
14. 后台发货管理中，未付款订单点击确认发货或已自提应失败。
15. 发货订单填写快递公司和快递单号后点击确认发货，订单应变为 `shipped` 并写入 `delivery_logs`。
16. 自提订单点击已自提后，订单应变为 `picked_up` 并写入 `delivery_logs`。
17. 已发货或已自提订单点击标记完成后，订单应变为 `completed` 并写入 `delivery_logs`。
18. 用户端订单详情应能看到配送方式、配送状态、收货地址或自提信息、快递信息或自提完成信息。
19. 修改后台自提地址后，历史自提订单详情仍应显示创建订单时保存的 `pickupInfo` 快照。
20. 非管理员调用 `updatePickupSettings`、`adminUpdateDeliveryStatus`、`uploadDeliveryImage` 应返回无管理员权限。

## 9. 合并发货

1. 同一客户两个已付款、发货、待发货订单可以创建一个 `shipment_groups` 记录。
2. 创建合并发货单后，关联订单写入 `mergeShipmentId`、`mergeShipmentNo`、`isMergedShipment`、`mergeShipmentStatus` 和 `shippingStatus`。
3. 创建合并发货单不修改订单金额、付款记录、客户账款和库存。
4. 不同客户、自提、未付款、已发货、已取消、地址不一致订单默认不能合并。
5. 确认发货后，合并发货单和所有关联订单同步为 `shipped`，并写入快递公司、快递单号和发货时间。
6. 未发货合并单可以取消，取消后只解除发货关联，不取消订单、不恢复库存。
7. 已发货合并单不能取消，可以标记完成。
8. 用户端订单列表和详情能看到合并发货状态、合并发货单号和物流信息。
9. `shipment_logs` 与 `admin_operation_logs` 应记录创建、更新、发货、取消、完成和导出。
10. 导出合并发货拣货单时，商品数量应按商品聚合，地址和手机号按权限脱敏。
